# Fast Core Scheduling with Userspace Process Abstraction 笔记

## 针对的问题

### 背景

CPU性能提升跟不上网络/磁盘的硬件提升，为了节省性能，很多系统采用内核旁路来提升性能。内核旁路将硬件映射到用户空间，并且使用run-to-completion（RTC），依赖核心绑定和轮询。

在云应用（微服务、无服务器等）中，通常使用工作负载整合，即将延迟敏感应用（L-app）和尽力型应用（B-app）打包在一起发布到服务器中，让L-app没用完的CPU周期能够被B-app使用，从而省下CPU资源。

但内核旁路与工作负载整合难以兼容，因为内核旁路需要绑定核心，导致CPU核心不能在应用间共享。如果将轮询的线程整合到一个核心上，由于内核调度器使用ms级的时间片，导致很高的延迟。而L-app对延迟敏感，并且负载可能突然出现，需要预留空闲的核心，与工作负载整合的省CPU资源相矛盾。

> 我查了一下，L-app的例子有：音视频通话、网络游戏等，B-app的例子有：编译任务、机器学习、科学计算等，关键区分是L-app关注低延迟，B-app关注高吞吐量。

### 现有系统

现有系统实现了用户空间核心调度器，实现工作负载整合，但在高密度的任务整合时，仍然有明显的CPU效率浪费，例如Caladan将L-app和B-app整合时，性能比单独运行差18%，多个L-app整合时会增加数倍延迟。

根本原因是：这些系统依赖Linux的进程模型，在一个核心上切换两个应用时需要进入内核切换地址空间。例如Caladan的一次核心分配包括了一次IPI和四次特权级切换，浪费了大量CPU周期。

### 核心问题

让CPU核在用户态直接进行进程切换，同时不违反内核进程的语义。同时需要支持抢占式调度。

需要借助两个技术：用户态中断（Uintr）和内存保护键（MPK，指为不同的内存设置不同的保护键，实现不同应用共享同一个地址空间，但互相不可访问。同时为CPU核心添加一个PKRU寄存器，来实现内存访问限制，延迟低。Linux提供了使用MPK的API）

## 设计：uProcess抽象

多个uProcess共享同一地址空间，借助MPK实现页面保护和隔离。多个uProcess构成一个调度域。同一调度域内的uProcess使用共享内存地址空间（SMAS）来保存代码段、数据段、栈等内容，实现用户态的进程切换。同时借助Uintr实现抢占。

uProcess创建时借助类似Linux的进程（kProcess），先在kProcess中创建线程，然后绑定在CPU核心上，进入用户态运行。uProcess与kProcess不一一绑定，是m:n关系

### 地址空间

将一个完整的地址空间划分成两个大区域：特权区和非特权区。

非特权区中存储各个uProcess的数据段、代码段等内容。每个uProcess都有一个独立的MPK，uProcess只能对自己的区域进行读写。代码段特殊，所有人都能读和执行，从而实现跳转。误执行其他uProcess的代码时由于不能读数据，能够发现错误。其他uProcess的区域不可见，特权区域不可见。此外，对调用门读和执行权限，对消息管道只读。

特权区中存储runtime的数据。处于特权区时可以操作整个SMAS的所有内容。进入特权区必须通过调用门进入，对外提供调度原语、内存分配等系统级的操作。

消息管道是一个特殊的内存区域，由运行时向uProcess提供一些信息，是一个单向的通信路径。运行时对其可以读写，各个uProcess只读。

### 调用门

uProcess的威胁模型是：只信任操作系统内核、硬件，uProcess的运行时、调度器和管理器。对应用代码、共享库、静态库不信任。

因此，uProcess进入特权区域时必须通过类似trap的过程，需要由调用门作为进入特权区域的方式。调用门的流程是：
1. 写pkru寄存器为运行时键，进入特权区域
2. 切换到运行时的栈
3. 执行特权操作
4. 切换回uProcess的栈
5. 写pkru寄存器为uProcess的键
6. 检查是否成功写回，不成功回到5

为了防止攻击进行的安全手段有：
1. 代码检查，检查WPRKRU指令、mmap、mprtect指令，对这些指令改为通过调用门由运行时完成。
2. 为了防止用户共享库中，恶意程序修改PLT表的攻击，执行特权操作的函数由函数指针实现，具体函数写在消息管道中，用户代码可读，实现地址的直接引用，不使用PLT表
3. 为了防止同一uProcess的线程修改了提权线程的寄存器，而导致ret后到其他位置，需要进行第2和第4的栈的切换。将CPU核心和所使用的栈映射到通信管道中。
4. 为了防止控制流劫持攻击，需要第6的检查键写回。

### 信号处理

由运行时注册用户态中断处理器，然后为调度域内的每个核建立无锁的FIFO队列。发送抢占时，调度器先将要运行的线程放入FIFO队列，然后向被抢占的核心发送uintr。收到后，这个核心上执行用户态中断处理器，通过调用门进入运行时的处理函数，运行任务。

由于uProcess共享地址空间，且能在kProcess之间互相运行，出现如内存损坏时可能导致其他kProcess也停止。对此，让uProcess的运行时也注册一个内核信号处理器，出现故障时经过调用门进入运行时，找到出错的uProcess后，广播到相关核的FIFO队列中。这些核在下次进内核时进行处理或终止。

### 上下文切换

两种切换方式都支持：让权和抢占。

让权式：通过调用门进入运行时，主动让权。

抢占式：当高优先级任务被低优先级任务阻塞时：
1. 调度器向被抢占的核心发送uintr。
2. 被抢占核心通过调用门进入运行时代码，将上下文保存在任务队列中，其中的返回地址是运行时返回的位置
3. 从运行时的任务队列中选择新线程，属于另一uProcess，恢复这个线程上下文并跳转到保存的位置。同时更新栈指针寄存器和PKRU寄存器
抢占式不需要进入内核。

### 调度器

运行时为每个核心维护一个FIFO队列，可以是不同进程的线程。调度器复用Caladan的指标（排队延迟、处理时间等）来实现负载平衡。

核心过载时，如果在运行B-app，则抢占；如果允许L-app，则从FIFO中弹出一个线程，重新分配到其他核心。

核心没有任务时，从FIFO中取任务，FIFO为空时从全局队列中取B-app，全局队列为空时通知调度器并进入空闲。

## 实现：Vessel

Vessel实现了uProcess，在Linux5.16.15和glibc中实现。对Linux内核的修改是增加Uintr的补丁。

### 管理器

负责管理uProcess的创建与销毁。创建时先通过fork创建一个kProcess，并绑定到指定的核心上。将SMAS映射到自己的虚拟地址空间，并开始轮询新命令。同时为这个kProcess分配uProcess，设置权限，进行初始化。销毁时管理器向uProcess内所有核心发送一个终止命令，这些核心在之后进入特权模式时终止uProcess。

### 运行时

分为程序加载器、线程管理、内存分配器、系统调用、网络与储存五个方面。
- 程序加载器：对链接器进行了部分修改，将mmap修改为SMAS内的mmap。同时进行安全检查和PKRU寄存器的初始化。
- 线程管理：由用户态管理，内核不知道这个线程。创建线程的系统调用替换为运行时内的线程创建。每个核心都有任务队列来保存分配给他们的线程
- 内存分配器：使用jemalloc管理uProcess的堆空间，将mmap系统调用拦截并替换为jemmaloc的函数
- 系统调用：内核系统调用会出现问题，因为uProcess可以对应到不同的kProcess上，会有安全性和正确性问题。因此把所有系统调用都拦截并通过调用门定位到运行时。运行时创建有相同的ACL权限的kProcess来执行
- 网络与储存：为uProcess提供绕过内核的网络与存储库，复用了Caladan的网络数据平面。

### 语义局限性

- 创建：由于uProcess由管理器创建，SMAS内地址相对固定。因此位置相关的程序可能导致内存地址冲突。因此uProcess只支持PIE编译链接的应用与库；
- 运行：信号与系统调用与Linux语义不同。需要先向运行时注册信号处理程序，由运行时代理信号的发送；系统调用会被拦截与替换，由运行时统一处理。
- 终止：不支持直接终止某个uProcess中特定线程，因为Linux内核无法感知。需要使用带参数的sigqueue系统调用来指定线程ID

此外，fork时父子uProcess不能共存在一个调度域，需要新建新的SMAS与调度域；按需加载时需要先将库加载到SMAS设置权限为不可写不可执行，然后执行代码检查，才能设置为可执行。

## 实验测试

负载：L-app：内存键值储存Memcached、内存OLTP数据库Silo；B-app：CPU密集型Linpack、自己实现的访存和计算交替的membench

对比：Caladan、Arachne、Linux CFS

### 核心重分配

将L-app与B-app中Linpack整合到一起，随着L-app吞吐量证据，Vessel总吞吐量几乎不变，平均下降6.6%；而Caladan平均下降16.1%；Arachene平均下降40%，Linux CFS吞吐量下降不多，但L-app延迟变高非常明显。

原因可以总结为L-app停止时，Vessel可以立刻扫描当前核心的任务队列取出B-app；L-app工作时B-app的核心可以不用进内核就完成抢占。两者都省去了进入内核的开销

### 密集整合

在一个核心上运行多个memcached实例（L-app）只与Caladan比较，其他系统延迟高出数量级。结果是在10个实例时，Vessel吞吐量与延迟基本不变，但Caladan最高吞吐量下降25%，延迟提升了20%。

原因总结为多L-app整合导致频繁的切换。Caladan的切换开销更大，Vessel能够跨uProcess重分配。

### 微基准测试

1. 上下文切换延迟：让两个单线程应用反复调用park，以park前后时间戳的一半为比较单位。Vessel平均0.161微秒，Caladan平均2.103微秒。因为Vessel的uProcess是纯函数调用，不用进内核
2. 缓存友好：两个应用同时随机读一个均匀分布的数据，Caladan不命中率是4.6%，Vessel是0.0415%，显著下降。因为共享地址空间对缓存更友好。
3. CPU核心扩展：单个Vessel调度域最多能支持42个核。核心数从32到44逐渐增多时，有效吞吐量提升了约22.81%，而Caladan肢体上了1.45%
4. 内存带宽控制：L-app与访存密集的B-app整合时，Vessel的总吞吐量比Caladan高43%，同时可以更准确的控制内存带宽的消耗。

## 我的思考

论文关注的最核心问题是：让进程调度也在用户态完成，不需要进内核。论文的表示是在用户态直接让CPU核心在进程间切换，是另一个分析的角度，本质相同。

传统的进程模型是绝对不能完成的。uProcess的本质就是在用户态再次实现了一个类似用户级线程的新的进程模型，然后与传统的kProcess进行m:n映射。
1. 用SMAS共享内存空间，MPK实现地址空间隔离，模拟kProcess的页表实现的隔离，同时减少切换页表的开销
2. 用uintr实现抢占
3. 运行时模拟了内核的作用，uProcess的控制层基本都是运行时完成的。
4. 调用门模拟了trap的过程，进入运行时的逻辑与trap非常相似
5. 调度器更多的考虑uProcess的调度，对kProcess调度过程基本没有考虑

此外，感觉论文分析核心与任务的关系时，视角与我不太相同。论文中更关注的是任务运行是不移动的，而是为任务分配核心；我则习惯于认为核心是不移动的，只是把任务挪到核心上运行。这种视角会带来一些数据结构定义的区别，比如论文中提到的CPU_map。
