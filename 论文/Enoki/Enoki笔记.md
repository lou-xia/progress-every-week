# Enoki 笔记

## 现有问题

在linux内核开发调度器的过程效率很低，主要因为
1. 任务的特性在发生改变：很多任务更短小，对延迟更敏感。
2. 硬件改变：存在异构的硬件与加速器
3. 任务自己携带的工作负载信息无法察觉
4. 机器负载不高也不低时最高效

而Linux现有的3种主要调度器存在代码量大、错误多。在内核进行开发时存在问题：
1. 容易出错：代码量大导致新代码会带来新的错误，可能有严重问题
2. 与用户交互有限：无法实现内核与用户地址空间的任务交互
3. 更新需要停机：需要重新编译，但公有云提供商会限制重启频率
4. 难以调试：缺乏有效的内核调试工具
5. 资源共享：不同任务可以使用不同调度器，需要在调度器间共享核心与周期

## 设计

### 总体架构

分为Enoki-C和libEnoki。

Enoki-C编译进Linux内核，直接与内核的数据结构和调度代码进行交互。主要负责：维护调度器的创建销毁与升级、修改任务数据结构、修改队列数据。并将核心调度器的调用转换成同步的接口，通过“message”来进行接口的信息传递。

libEnoki与调度器代码一起编译成动态加载的内核模块。提供安全接口用于调度器访问内核。libEnoki中的处理函数从“message”中提取信息，传递给被调用的调度器函数，将返回值也通过“message”返回给Enoki-C。

这里的调度器应该指的是侠义的调度器，只包括了选择下一任务以及维护队列的功能。

### 安全接口

Enoki提供安全的接口，包括需要调度器实现的和供调度器使用的接口，从而让调度器可以完全用安全的rust来实现。

供调度器使用的接口：锁和定时器，文中没有详细说明

需要调度器实现的接口：由Enoki-C将Linux核心调度器的接口转换为“message”的接口，经过libEnoki中的处理函数解析“message”，传递给被调用的调度器。在这个逻辑上，借助rust的trait实现了若干个接口，需要调度器实现。

为了解决选择任务接口中可能存在的任务无法运行的情况（比如队列里没有这个任务。即使这是一个语义错误，也尝试捕获这个错误），定义了一个Schedulable类型，表示任务可以在哪个核心上安全调度。Schedulable无法被复制和克隆，在任务被分配到不能正常调度的核心时，返回pnt_err，来防止内核崩溃。这个机制目前还存在一定的局限性

### 热升级

Enoki支持的调度器可以进行热升级。原理是调度器只有在被内核（或者说Enoki-C）调用时，才会出现状态不一致的问题。因此为调度器加读写锁。非升级调用获取读锁，升级调用获取写锁，保证在升级过程中没有新的调用发生。升级完成后，只需要在Enoki-C中交换指针指向新模块。有一定的限制：一定要中断服务、新旧调度器用于传递状态的数据结构必须在内存结构上一致。

### 自定义调度器提示

指的是有些用户任务希望在指定的核心运行，或者某些用户任务在同一个核心上效果更好（NUMA，非一致性内存访问）。此外，还需要内核向用户空间传递消息，比如核心变成可用，或者其他任务在内核阻塞。

提示信息的数据结构由调度器定义，并且只要数据结构不变，热升级时也可以共享。

### 记录与回放

记录所有对调度器的调用与调度器提示，发送给用户态的记录程序。回放时在用户态把记录的内容发送给调度器，保证加锁的严格顺序

## 实现与测试

实现时参考了前置工作Bento，以安全的Rust为主进行编写（Enoki-C用C编写）。同时设计测试了一系列调度器，包括WFQ（简化的CFS）、shinjuku、locallity-aware、Arachne两级调度器。

测试从两个角度分析：性能延迟（主要来自Enoki与调度器的4次接口通信）与扩展性（多线程时测试）。机器是一种是8核单路机器，配备运行频率为 3.00GHz的Intel i7‐9700CPU;另一种(用于可扩展性测试)是80 核双路机器,配备运行频率为2.00GHz的Intel Xeon Gold 6138 CPU。

WFQ：使用NASA的NAS并行测试评估，与CFS比较。结果是平均性能差是0.74%，最坏情况是8.57%

shinjuku：使用RockDB测试，比较CFS、ghOSt‐Shinjuku和Enoki‐Shinjuku。结果是只有RockDB时高吞吐时CFS延迟高、同时运行RockDB和一个批处理时，CFS延迟明显高，高负载下ghOSt的吞吐量差。

局部感知调度器：使用schbench测试，比较CFS、CFS的cgroup、局部感知但随机提示、局部感知。结果是CFS与局部感知随机提示性能近似，说明是提示信息起到了左右。局部感知效果最好

Arachne调度器：使用Facebook ETC测试。结果是与原版的Arachne调度器效果相近。高负载情况延迟明显低于CFS。

热升级：性能影响很小，在单路机器上延迟是1.5μs，双路机器上延迟是10μs左右。

记录与回放：记录显著慢于正常运行，回放更慢。主要原因是保持锁的顺序一致

## 我的思考

论文关注的问题是：调度器（指选择下一任务）的开发过程难，分成了：
1. 会出现大量错误 -> 使用rust语言保证安全，同时使用安全接口保证模块间安全，此外还用schedulable来catch一些语义错误
2. 每次更新都要重新编译 -> 热升级
3. 调试困难 -> 记录与回放
4. 用户信息无法考虑到 -> 用户提示

Enoki-C仍然编译进了内核，用于处理与Linux的核心调度器的交互

libEnoki是对用户（编写调度器者）的接口

重点是开发了一个方便Linux调度器开发的框架，从而能够实现以较小开销实现方便的开发，同时能够解决一些开发困难的问题。
