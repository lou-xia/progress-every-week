1. 任务树：AsyncOS在论文和代码中都没有提到具体的任务数概念。我思考后的理解是一个逻辑上的树，内核调度器是根，内核任务和用户调度器是下一级树根，用户任务是树叶。感觉可以把用户调度器当作内核调度器的一个任务，这样选择地址空间的过程就变成了选择优先级，运行任务的过程是单独的路径，即切换地址空间、构造中断上下文、进入into_user接口的过程。与之前的路径是基本相同的。
2. 恢复用户线程问题：用户调度器可以直接恢复线程上下文，即yield让权的线程。对于被中断而产生的线程，例如时钟中断发生，用户调度器没有办法直接恢复。需要借助一条单独的路径（绿色线）进入内核来恢复。这样会出现内核态（发生中断）-用户态（选择调度器并回到用户态）-内核态（无法恢复线程再进内核）的开销。目前没有想到好的解决方案，关键问题是时钟中断发生时意味着需要切换任务，一定会出现这种情况。其他外部中断可以在trap_handler中回到原任务。
3. 系统调用：发生系统调用后，在trap_handler处理之后，可以直接回到发起系统调用的任务内部，也可以选择into_user接口回到用户态调度器，相当于重新考虑优先级等问题。是否有必要？这种情况算异步系统调用吗？
4. 调度器支持waker的问题：用户任务存在这种情况：
```rust
async fn user_task {
    let res = async_read().await;
}
```
这种情况下，如果async_read返回pending时，user_task需要阻塞。需要注册waker来通知user_task的唤醒？
